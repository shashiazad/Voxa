## Load (concurrent sessions on one node)

**Result: 100 sessions per node was NOT reached on this machine.** The three worker processes plateau at about 4.7 CPU cores (≈ 1.5 cores per Python process: the GIL bounds one process) and voice-to-voice stays under ~0.9 s up to 20 sessions (p95 1.29 s at 30); at 40 sessions replies stop arriving (overload, no reply measured). So one worker process handles roughly 10-12 calls; 100+ sessions per node means ~9 worker processes on ≥ 16 cores, which is what the Helm defaults assume (`maxSessions: 12`) but which was not demonstrated here. The generator, the SFU and Docker share the same 10-core laptop VM, so absolute numbers are pessimistic; STT/LLM network latency and rate limits are excluded by design. The 'dropped frames' and 'NS+VAD' columns are empty because the Prometheus query returned no data during this run. Before the thread-mode fixes in this phase (shutdown hangs, polling playout) leaked sessions kept burning CPU after calls ended.

## Caveats that apply to every number above

- Free-tier Groq limits dominated the LLM results: `qwen/qwen3.8-27b` has a 200 k tokens/day quota that was exhausted by testing, so the latency run was served almost entirely by the fallback `openai/gpt-oss-20b` (slower first token). Earlier, small, un-gated measurements with qwen as primary gave 0.8-1.1 s client-measured voice-to-voice.
- The robustness matrix runs the agent with a mocked LLM so token limits do not skew interruption results; speech-to-text is the real Groq Whisper.
- The load test uses stub STT and a mock LLM (cloud calls excluded by design) and shares one 10-core laptop VM with the load generator and the SFU.
- No real microphone/speaker hardware, other browsers or networks were tested; echo is simulated (residual after AEC), background voices are synthetic (`say`).
